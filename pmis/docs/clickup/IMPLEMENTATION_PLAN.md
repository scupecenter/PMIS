## 0. الملخص التنفيذي

- **المستودع:** نستورد الشجرة الفرعية `pmis/` مع `.claude/` و`.github/` من `My_Repo` بتاريخها الكامل إلى `PMIS` باستخدام `git filter-repo`، ونُبقي المسار `pmis/` كما هو كي لا نعدّل 108 مراجع للمسار في 35 ملفًا (CI والوكلاء وسكربتات التثبيت). نستبعد `PMIS_Site_Master.xlsx` (2.7 ميغابايت) ومجلد `build/` من التاريخ. بعد ذلك نطوّر الواجهة في مكانها، `pmis/apps/web`، دون إعادة كتابة.
- **الحوكمة:** `main` محمي. لكل مرحلة فرع تكامل اسمه `phase-N/<slug>` وطلب دمج واحد (PR) بحالة مسودة نحو `main`. المهام الصغيرة تُدمج في فرع المرحلة بطلبات قصيرة. لا يُدمج فرع المرحلة في `main` إلا بعد موافقة المالك على بوابة المرحلة.
- **الوكلاء:** الجلسة الرئيسية تنسّق ولا تقرأ الملفات الكبيرة. كل مهمة محدودة تذهب إلى وكيل واحد، ويأخذ الوكيل مسارات الملفات لا محتواها، ولا يتجاوز تقريره 300 كلمة. العمل الآلي يذهب إلى `hzblj-skills:fast-worker`.
- **قرارات المالك المحسومة (2026-11-08)، وهي ملزمة في كل المراحل:**
  1. **الخط العربي:** Cairo، وهو الخط الحالي، ويُقرن بـ Inter للنص اللاتيني.
  2. **النسخة الافتراضية:** `neutral`، المطابقة لـ ClickUp. النسخة `pmis` تبقى متاحة بمفتاح تبديل.
  3. **تخطي المحطات:** مسموح فقط بعد أن تُظهر نافذة قائمة البوابات أن كل البوابات مستوفاة. يُسجَّل النقل محطةً محطة، بانتقال واحد لكل محطة، ولا يُسجَّل أبدًا كقفزة واحدة.
  4. **قائمة ClickUp التجريبية** ("PMIS Sites (sandbox)") تبقى حتى نهاية المشروع، مرجعًا بصريًا.
- **ثلاث نتائج من الكود تغيّر الخطة** (التفصيل في §7):
  1. لا توجد نقطة اتصال تنقل الموقع إلى المحطة التالية. المحطة تكتمل حين تُعتمد مهمتها (`sites.service.ts:131,139`). لذلك يصبح الإفلات على عمود في Board فتحًا لإجراء المهمة القائم، لا "نقلًا" للموقع.
  2. واجهة حفظ العروض تستوعب الفلاتر المسطّحة والأعمدة والفرز، ولا تستوعب كائن العرض الموحّد كاملًا دون تغيير. سبب ذلك أمني: الدالة `sv_strip` تزيل مفاتيح الفلاتر من المستوى الأعلى فقط.
  3. الفرز على الخادم موجود في `/sites` وحدها. السجلات (registers) تدعم البحث `q` ولا تدعم الفرز، وحجم الصفحة الأقصى 200 صف، ولا توجد نقطة بحث شامل.

### 1.3 الأوامر بالضبط (الخيار أ)

```bash
# 0) الأداة
pip install --user git-filter-repo           # أو: apt-get install git-filter-repo
export PATH="$HOME/.local/bin:$PATH"

# 1) نسخة نظيفة ومنفصلة من المصدر. filter-repo يرفض العمل على نسخة عادية، ولا نلمس /home/user/My_Repo
git clone --no-local --branch main --single-branch \
  https://github.com/scupecenter/My_Repo /tmp/pmis-import
cd /tmp/pmis-import
git rev-parse HEAD > ../IMPORT_SOURCE_SHA     # نقطة الاستيراد (يُتوقع 90726cd)

# 2) تحليل قبل الحذف
git filter-repo --analyze
less .git/filter-repo/analysis/path-all-sizes.txt

# 3) نُبقي المسارات المطلوبة. كل ما عداها يُحذف من التاريخ (PMIS_Site_Master.xlsx و build/ و README.md الجذري)
git filter-repo \
  --path pmis/ --path .claude/ --path .github/ \
  --path .gitignore --path .mcp.json

# 4) تحقق
git log --oneline | wc -l                      # أقل من 167 بعد حذف الـ commits الفارغة
git rev-list --objects --all | grep -i 'Site_Master' && echo "FAIL" || echo "xlsx gone"
du -sh .git
docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:v8.21.2 \
  detect --source /repo --log-opts="--all" --redact --report-path /repo/../gitleaks.json
# أو بلا Docker: gitleaks detect --log-opts="--all" --redact

# 5) الدمج في PMIS مع الإبقاء على README الموجود
cd /home/user/pmis
git checkout -b phase-0/import origin/main
git remote add import /tmp/pmis-import
git fetch import main
git merge --allow-unrelated-histories import/main \
  -m "Import PMIS Workspace from My_Repo@$(cat /tmp/IMPORT_SOURCE_SHA) via git filter-repo (pmis/, .claude/, .github/)"
git remote remove import
git push -u origin phase-0/import
gh pr create --repo scupecenter/PMIS --base main --head phase-0/import --draft \
  --title "Phase 0: import PMIS Workspace history and green CI" --body-file .github/pull_request_template.md
```

ملاحظة: نافذة الطلب على GitHub ترفض المقارنة بين تاريخين بلا أصل مشترك. لهذا يجري الدمج محليًا أولًا، فيصير للفرع `phase-0/import` أصل مشترك مع `main`، ويُفتح الطلب بشكل عادي.

**المزامنة التزايدية قبل التجميد:** filter-repo حتمي، فالمُدخل نفسه يعطي قيم hash نفسها. إن دُمج شيء في `My_Repo` بعد الاستيراد، نعيد الخطوات من 1 إلى 3 على `main` الجديد، ثم نعيد الجلب (fetch) والدمج، فلا تدخل إلا الـ commits الجديدة.

### 2.2 CI

نبدأ من `ci.yml` المستورد كما هو (أربع jobs: `api` و`web` و`contract` و`installer`)، ونجري عليه أربعة تعديلات صغيرة فقط (يملك `.github/` الوكيل `devops-security`):

| التعديل | التفصيل | المرحلة |
| --- | --- | --- |
| المشغّلات | `pull_request.branches: [main, 'phase-*']` كي تُفحص طلبات المهام نحو فروع المراحل | 0 |
| `web`: الأنواع والتنسيق ووحدات vitest | موجودة اليوم (`npm run typecheck`، `lint`، `test`، `build`). لا تغيير | 0 |
| job جديدة `e2e-matrix` | Playwright بأربعة مشاريع (projects): `en-light` و`en-dark` و`ar-light` و`ar-dark`. كل مشروع يضبط تفضيل اللغة والسمة المخزّن عبر `addInitScript` قبل التحميل، بالمفاتيح نفسها التي يستخدمها التطبيق (`src/lib/localPref.ts`). يُضاف المحور `preset` (`pmis` و`neutral`) في المرحلة 1 لاختبارات الشكل فقط، لا لكل الاختبارات، كي لا يتضاعف الوقت | 0، و1 للـ preset |
| فحص الحجم | سكربت بلا اعتماديات جديدة (`pmis/apps/web/scripts/bundle-budget.mjs`) يقرأ `dist/assets/*.js` بعد الضغط gzip ويقارنه بالملف `bundle-budget.json`. يفشل عند تجاوز الميزانية | 1 |
| فحص الملفات الكبيرة | `git diff --stat` على الطلب. أي ملف ثنائي يتجاوز 1 ميغابايت تحت `pmis/apps/` يُفشل الفحص | 0 |

Chromium مثبّت مسبقًا في `/opt/pw-browsers/chromium`، والإعداد `playwright.config.ts` يستخدمه، فلا نحتاج `playwright install` محليًا. على مشغّلات GitHub يبقى ما يفعله `ci.yml` اليوم كما هو.

لقطات الشاشة المرجعية للانحدار البصري (`toHaveScreenshot`) تُولَّد على Linux داخل CI فقط، ويُحدَّث خط الأساس بأمر صريح (`--update-snapshots`) في commit مستقل بعنوان `baseline:`، كي لا يختبئ تغيير بصري داخل commit كود.

## 3. تنسيق الوكلاء بأقل استهلاك للرموز

### 3.1 القواعد

1. **مهمة واحدة محدودة لكل وكيل.** حدود المهمة: ملفات محددة، ونتيجة قابلة للاختبار، ولا تتجاوز طلب مهمة واحدًا.
2. **مسارات لا محتوى.** الموجز (brief) يذكر المسارات وأرقام الأسطر وأرقام البنود ("clone-spec §9، الأسطر 167 إلى 189")، ولا ينسخ نصها. المواصفات تُنسخ إلى المستودع في المرحلة 0 (§4) كي يقرأها الوكيل من مسار ثابت.
3. **تقرير لا يتجاوز 300 كلمة.** يذكر ما تغيّر (مسارات)، ونتائج الاختبارات (أرقامًا)، وما لم يُنجز، والمخاطر. لا يلصق كودًا إلا سطرًا تتوقف عليه نقطة.
4. **العمل الآلي للوكيل الرخيص.** إعادة التسمية، ونقل جدول إلى `DataTable` بنمط موحد، وإضافة مفاتيح i18n، وتحديث لقطات، وتعديل المسارات: كلها لـ `hzblj-skills:fast-worker`.
5. **التوازي للمستقل فقط.** مهمتان تعملان معًا فقط إن لم تشتركا في ملف ولا في رمز تصميم. عند الشك ننفّذ بالتتابع.
6. **الجلسة الرئيسية تنسّق فقط.** لا تقرأ ملفًا يتجاوز 200 سطر، ولا تقرأ الدراسة ولا المواصفة ولا `openapi.yaml`. إن احتاجت إلى حقيقة سألت وكيل `Explore` سؤالًا واحدًا محددًا، وطلبت الجواب مع file:line.
7. **ملكية الملفات** حسب `ORCHESTRATION.md`. لا يكتب `frontend-engineer` في `apps/api` أبدًا. أي حاجة في الواجهة الخلفية تُفتح كمهمة منفصلة تحتاج موافقة.
8. **لا إعادة قراءة.** التقرير السابق يُمرَّر للوكيل التالي كمسار ملف (`pmis/docs/clickup/reports/N.x.md`) لا كنص.
9. **إيقاف مبكر.** إن وجد وكيل أن المهمة تحتاج تغييرًا في الواجهة الخلفية أو قاعدة البيانات أو الصلاحيات، يتوقف ويذكر ذلك في تقريره، ولا يلتف على القيد.

## 6. الضوابط

1. **لا تغيير في منطق الأعمال أو الصلاحيات أو قاعدة البيانات دون موافقة منفصلة.** أي طلب يلمس `pmis/apps/api/**` أو `pmis/db/**` أو `pmis/contracts/**` يحتاج قرارًا مكتوبًا من المالك يُذكر رقمه في الطلب، ويتبع قاعدة "العقد أولًا" وقاعدة المرايا (`prisma/migrations` = `db/sql`) القائمتين في المستودع. البند 7 في §2.3 يفحص ذلك آليًا.
2. **البوابات مفروضة في السحب والتحرير المباشر والإجراءات الجماعية:**
   - حقول المحطة والمرحلة والحالة والبوابة لا تُحرَّر مباشرة في أي مكان. تُعرض للقراءة فقط مع أيقونة `Lock`، والنقر يفتح نافذة الموقع على قسم "المحطات والبوابات". اختبار وحدة يمر على كل ColDef.
   - السحب يُفحص أثناء المرور فوق العمود من رد الخادم (`pipeline[].state` و`lock_reasons`)، والعميل لا يقرر البوابة. الإفلات لا يكتب إلا عبر إجراء المهمة القائم، ورد الخادم نهائي.
   - الإجراءات الجماعية لا تتضمن أي انتقال بوابة: لا نقل محطة، ولا اعتماد، ولا رفض، ولا إغلاق، ولا إلغاء، ولا إعادة فتح. اختبار وحدة يمر على كل السجلات.
   - كل كتابة تمر عبر الواجهة البرمجية القائمة، وفحص الصلاحية، وStepUp، ونافذة السبب. الأعمدة المخفية والممنوعة تبقى خاضعة لـ `reconcile` في `tablePrefs`.
3. **لا يُنسخ كود ClickUp ولا أصوله:** لا كود، ولا أيقونات (نستخدم lucide)، ولا شعار، ولا رسوم، ولا نصوص، ولا التدرج اللوني للعلامة (`#FF02F0 > #FC6D2D > #6647F0 > #0091FF`)، ولا اللون البنفسجي. نعيد إنتاج الأنماط والأبعاد والكثافة والتوقيت فقط، ونكتب كل النصوص من جديد بالعربية والإنجليزية. الإطارات المرجعية لا تدخل المستودع ولا الحزمة.
4. **بيانات اصطناعية فقط** في الاختبارات واللقطات، حسب قاعدة المستودع.
5. **الميزات المستبعدة** (من المواصفة §0.5):

## 7. القرارات المفتوحة والقيم الافتراضية الموصى بها

### 7.1 إجابات الأسئلة الثلاثة من الكود

**(أ) هل توجد واجهة برمجية تعيد للموقع المحطات التالية المسموحة وما يمنعها؟ الجواب: نعم لموقع واحد، ولا للدفعة، ولا توجد أصلًا نقطة لنقل الموقع.**
- `GET /sites/{id}` يعيد `pipeline`، وهي عُقد المحطات والبوابات بالترتيب، لكل عقدة `state` (`done` أو `current` أو `locked` أو `na` أو `planned` أو `late`) و`lock_reasons` القادمة من `gate_eval()`: `apps/api/src/sites/sites.service.ts:410` (الاستدعاء)، و`:551-624` (البناء)، و`:600-615` (حالة البوابة وأسباب القفل).
- القائمة `GET /sites` تعيد `next_milestone` و`rail` فقط، بلا أسباب قفل: `sites.service.ts:341-366`.
- أسباب المنع لكل مهمة: `GET /tasks/{task_id}/blocked-by` (`contracts/openapi.yaml:10419`).
- المحطة تكتمل حين تُعتمد مهمتها، ولا يوجد انتقال مباشر: `sites.service.ts:131` (`is_milestone_task AND state='approved'`) و`:139`. ولا يحوي العقد مسارًا لنقل الموقع؛ إجراءات المهمة هي `/tasks/{id}/start|submit|review|approve|reject` (`openapi.yaml:3114-3243`).
- **العمل الخلفي المطلوب:** لا شيء للحد الأدنى، فطلب واحد لـ `GET /sites/{id}` عند بدء السحب يكفي، والمواصفة نفسها تطلب "طلبًا واحدًا عند بدء السحب". اختياري، بموافقة منفصلة: إضافة `lock_reasons` إلى عناصر `GET /sites` لعرض شارة القفل على البطاقات دون طلبات إضافية، وهو تعديل قراءة فقط في `siteItem()` مع رفع إصدار العقد.

**(ب) هل يستوعب تخزين العروض المحفوظة إعداد عرض JSON حرًا؟ الجواب: جزئيًا.**
- الجدول `saved_views` فيه ثلاثة أعمدة jsonb ثابتة: `filters` (كائن لا يتجاوز 16000 حرف) و`columns` (كائن) و`sort` (مصفوفة لا تتجاوز 5 عناصر): `db/sql/064_p10_saved_views.sql:42-44`.
- الواجهة البرمجية صارمة (`.strict()`): `columns` تقبل `order` و`hidden` و`width` و`density` فقط، و`sort` تقبل `{id,dir}` بحد 5، و`filters` سجل بقيم `unknown` بحد 50 مفتاحًا، وأي مفتاح أعلى غير معروف (مثل `grouping` أو `board` أو `gantt`) يُرفض: `apps/api/src/views/saved-views.service.ts:21-44`.
- **القيد الأمني:** `sv_strip()` تزيل للقارئ مفاتيح الفلاتر التي تخص أعمدة مخفية عنه، لكن **على المستوى الأعلى فقط** (`064_p10_saved_views.sql:260-265`). أي فلتر متداخل يشير إلى عمود ممنوع سينجو من الإزالة. وفلتر المنطقة في العرض المشترك يُفحص من `filters.region_id` في المستوى الأعلى (`saved-views.service.ts:104-113`).
- **الحل المؤقت دون تغيير (الافتراضي، المرحلة 4):** الفلاتر البسيطة بشرط AND، كل فلتر مفتاح مستقل في المستوى الأعلى، فيعمل `sv_strip` وفحص المنطقة كما هما. التخطيط غير الحساس (نوع العرض، والتجميع، وإعدادات Board والتقويم وGantt، وترتيب بطاقات اللوحة) يُحفظ في مفتاح واحد محجوز هو `filters._layout`، ويُصفّى عند القراءة بـ `reconcile` على العميل. مجموعات AND/OR المتداخلة تُحفظ في العرض الشخصي غير المشترك فقط، أو لا تُحفظ، حتى يُعتمد العمل الخلفي.
- **العمل الخلفي المطلوب (موافقة منفصلة، `database-engineer` و`backend-engineer`):** عمود `layout jsonb` مع قيد الحجم، وجعل `sv_strip` تتبع أعمدة `filter_groups` المتداخلة، ورفع إصدار العقد، وهجرة مع مرآتها. الحجم M.

**(ج) هل تدعم نقاط القوائم الفرز والبحث على الخادم؟ الجواب: البحث نعم في الأغلب، والفرز في المواقع فقط.**
- `GET /sites`: فرز على الخادم بثماني قيم (`site_code` و`region` و`stage` و`due_date`، تصاعديًا وتنازليًا) في `sites.service.ts:22` و`openapi.yaml:2613`، وبحث `q` في `sites.service.ts:198`.
- `GET /registers/{key}/records`: بحث `q` على رمز الموقع ونص بيانات السجل في `registers.service.ts:395-396`، و**لا فرز**، فالترتيب ثابت `ORDER BY r.created_at DESC` في `registers.service.ts:402`، والمؤشر (cursor) مبني على `created_at`. حجم الصفحة الأقصى 200 (`common/cursor.ts:21`).
- العقد كله يحوي معامل `sort` في موضع واحد هو `/sites`، ومعامل `q` في 20 موضعًا، ولا مسار `/search` عامًا.
- **العمل الخلفي المطلوب (موافقة منفصلة):** (1) معامل `sort` بقائمة سماح لكل سجل، مع مؤشر keyset لكل فرز، في `registers.service.ts` و`openapi.yaml`، وحجمه M؛ (2) اختياريًا نقطة `GET /search?q=` تجمع المواقع والسجلات المسموحة، وحجمها M. وحتى ذلك الحين: فرز على العميل حين تكتمل الصفحات (المرحلة 3)، وبحث موزّع في لوحة الأوامر (المرحلة 2).
